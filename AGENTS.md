# Project rules

- RayProp partner listings use ids prefixed `rp_` and `source: "rayprop"`; all RayProp calls go through the `rayprop-api` edge function (x-api-key stays server-side). Why: keeps the key secret and lets local listings work when RayProp is off.
- RayProp amounts are kobo; convert only via `koboToNaira` (`src/lib/rayprop-map.ts`, `_shared/rayprop-core.ts`). Why: avoids 100x price bugs.
- Partner bookings are reserved and wallet-paid server-side in `paystack-verify` after Paystack succeeds; failures are saved as `needs_attention`, never dropped. Why: a paying guest must always have a booking record.
- Pure RayProp helpers live in `_shared/rayprop-core.ts` (no Deno APIs). Why: vitest can test them.
- `rayprop-api` serves search/paging from a saved copy of the whole RayProp catalogue (`partner_catalogue`), refreshed page-by-page at most every 6 hours; a blocked/429 reply pauses all RayProp calls 30 min via `partner_sync_state` (helpers in `_shared/rayprop-core.ts`). Text matching lives in `raypropMatches`. Why: RayProp city filters miss area-labelled stays, and bulk reloads got our key blocked.
- Local-stay cancellation/refunds go only through the `cancel-booking` edge function using `_shared/cancellation-core.ts` (pure, tested). Why: refund math and Paystack refund must be server-side and single-sourced.
- Places live in the `locations` table (state → city → neighbourhood, with aliases); listings link via `state_id/city_id/neighbourhood_id` set by the `listings_location_sync` trigger using `match_location`, and partner stays via `partner_location_map` (filled by `rayprop-api` on catalogue load). Low-confidence matches go to review at /admin/location-audit, never guessed. Why: one source of truth for place names across local and partner stays.
- Search "Where" suggestions come only from the `search_locations` / `popular_locations` / `search_stays` database functions; a picked place is stored in the link as `loc` (slug) + `loc_type`, and results filter local stays by place ids and partner stays via `rayprop-api` `location_id`. Free text without a pick falls back to text matching. Why: one de-duplicated place list for suggestions and results.
- Paystack charge.success is handled in `paystack-transfer-webhook` (single Paystack webhook URL); partner fulfilment lives in `_shared/partner-fulfil-booking.ts`, insert-first as `processing`. Why: Paystack allows one webhook URL and bookings must survive a closed tab.
- Guest problems (support) are created and moved only through the `create_support_issue` / `guest_issue_action` / `staff_issue_action` database functions; admin RLS uses `private.has_role`. Why: SLA times, notifications and audit are set in one place and internal notes never reach guests.
- Design tokens and type/radius scales (PRD §9) live in `src/index.css` + `tailwind.config.ts`; shared UI pieces in `src/ui/kit.tsx`; `npm run check:ui` must pass. Why: one look, enforced automatically.
- Guest navigation: tabs/menu items defined once in `components/shell/navTabs.ts`; phone/tablet (<1280px) use TopBar + BottomNav, PC uses `Dock` (edge/pin prefs in localStorage via `navPrefs.ts`). Why: one nav list drives every screen size.
- Admin navigation: sections, groups and queue counts defined once in `components/admin/adminNav.ts` (counts via `useAdminCounts`); next-step wording via pure helpers in `src/lib/next-step.ts`. Notifications are only a bell drop-down (`NotificationsBell`); `/notifications` redirects. Why: one source for admin nav and next-step copy.
- Business values (fees, markups, time limits, switches) live in the `app_settings` table, read via `useSettings` (client) and `_shared/settings.ts` (edge), with defaults in `src/lib/settings.ts`; never hardcode them. Why: admins change them without a code change, and screen and server agree.
- Booking lifecycle: local stays get a `held` row at payment start (`paystack-init`), confirmed only via `confirm_local_payment` (verify + webhook); moves are checked by `booking_status_guard` (mirror of `_shared/booking-core.ts`), every status change logs to `booking_events`, overlaps are refused by the `bookings_no_overlap` exclusion, and money split (fee/markup/host payout) is saved per booking. Clients never write `bookings` directly — they use `guest_confirm_checkin` / `staff_booking_action`. Why: one auditable path, no double booking, exact earnings.
- Local-stay pricing (date price > weekend price > base, weekly/monthly discount, cleaning fee, min/max nights) is computed only by `quoteLocalStay` in `_shared/booking-core.ts`, used by checkout and `paystack-init`; host blocks and imported iCal dates live in `listing_blocks` and are merged into `listing_booked_ranges`. Request-to-book bookings sit in `awaiting_host` until `host_booking_action`; declines/timeouts are refunded by the `booking-requests` function. Why: screen and server always agree on price and availability, and a paying guest is never left unrefunded.
